# StreamFlow Lite v0.1.25 (pre-release) — camera capture diagnosis

## Fixed (verified in code + tests; NOT yet verified on the reporting user's camera)
- **Explicit camera modes were never applied.** FFmpeg's dshow selects a
  compressed mode through `AVFormatContext.video_codec_id`, not an AVOption;
  the `vcodec=mjpeg` request was silently ignored. Now set on the context, and
  any option an input does not consume fails the attempt instead of being
  ignored.
- **60 fps requests rejected by most drivers.** dshow computes the frame
  interval as `den*10^7/num` (integer): "60" → 166666, while drivers advertise
  166667. We now request the exact advertised interval (`num:den`), then the
  plain rate.

## New measurements (Diagnostics → Video sources)
Per camera: camera-sent fps (packets), captured fps, fps reaching program,
decode ms, convert ms, camera→capture ms, longest gap in the last second,
skipped frames, decode/read errors, failed format attempts, and an automatic
verdict naming the limiting stage.

## Test pattern
Now a real test signal: 75 % bars, near-black/near-white clip steps, 11-step
grey scale, ramp, 1-px resolution patches, border + circle, moving bar,
frame-index boxes and a wall-clock timecode for glass-to-glass latency.

## Measured (dev VM, release build, synthetic 1080p60 MJPEG input)
capture ~31–33 fps published of 60 fps sent, decode ~7 ms, convert ~4 ms,
capture latency ~10 ms, longest gap 40–49 ms, 0 errors. Test pattern 1080p:
6.4 ms/frame (debug build).
Not measured: real Windows cameras (no camera in CI).
